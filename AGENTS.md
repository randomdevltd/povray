# Performance work

- Target the current `performance` branch for speed work. Use a separate branch and PR for each coherent change, and keep stacked changes based on their recorded fork points.
- Profile the phase and feature being changed before choosing an algorithm. Include preparation or map-building cost, trace cost, memory, and any work moved between phases.
- Use existing public scenes for ordinary behavior and regression checks. Add small public scenes that stress the expensive feature, including realistic combinations of media, photons, lighting, and geometry. A large integrated scene is useful as a final check, but it is not a substitute for focused measurements.
- Prefer user-space instruction counts with a matching parse-only run and repeated, alternating builds. Record whether counters were multiplexed. Treat CPU and wall times as supporting evidence, especially for small differences on a busy machine.
- Use `+PR` for renders; if anti-aliasing is needed, use method 4 (`+AM4`). Keep benchmark runs isolated enough to compare their instruction counts and images reliably.
- Check decoded images as well as speed. An exact-path optimization should preserve pixels. A new approximate mode should be judged against a high-quality reference for detail, noise, and artifacts, along with how easily users can tune it. Faster, cleaner results with fewer controls are more valuable than matching the old algorithm's errors.
- A well-measured gain in a narrow but realistic case is useful. Report the conditions that produce it and check ordinary scenes for regressions. Look for costs that multiply when effects are combined or sample counts rise.
- Preserve compatibility for released features, and never gate a feature on `#version`. A new keyword, block, option or capability works in every scene version, a 3.7 scene included: no version check, no warning that falls back for older versions, no "needs #version 4.0" note. A version gate has one legitimate use: changing the default of existing behaviour, so that older scenes keep rendering as they did. Explicit settings override defaults at every version.
- Legacy means syntax or behavior present in an official public release. Compatibility requirements currently apply to POV-Ray 3.7 and earlier; neither 3.8 nor 4 has been officially released. Unreleased features may be replaced or removed without treating the change as a compatibility break.
- Rework unreleased features directly: remove obsolete syntax, state, adapters, and documentation, and update affected scenes by hand. Do not retain compatibility shims, deprecation paths, or migration codemods for superseded unreleased iterations.
- Implement closely related performance opportunities within the current work when they can be measured and reviewed together. Propose a separate ticket for another subsystem or a substantial redesign.
- Give overlapping media and photon work distinct owners, then coordinate changes at their shared interfaces.
- Keep public code, fixtures, documentation, commits, and PR text about the code and reproducible public examples. Do not include private workload names or paths, board references, account details, or machine security settings.

# New scene syntax and features

- A new keyword, block or option is available at every `#version`. The `.pov4` language is a separate syntax layer the keyword must also land in; it is not a version gate.
- A new keyword or block has to land in every layer of the scene language at once, or the layers disagree. The classic parser: the token enum in `source/parser/reservedwords.h` and the word table in `source/parser/reservedwords.cpp` (contextual words are matched by their text where they apply and stay free as identifiers). The 4.0 language: a grammar rule in `libraries/tree-sitter-pov4/grammar.js`, and the evaluator and static checker in `source/parser/pov4.cpp` when the feature carries meaning there.
- Put a value-producing keyword in the category section that matches what it yields — the `*_TOKEN_CATEGORY` markers in `reservedwords.h` (signature, float, vector, colour, other). Those categories are the types the editor tooling and the `.pov4` static checker consume, so a misfiled keyword mis-types completions and checker diagnostics everywhere.
- Regenerate the derived language artifacts in the same commit; they are outputs, never hand-edit them. `node tools/language/keywords.mjs` (keywords.json from the reserved words). After editing `grammar.js`, `npm run generate` in `libraries/tree-sitter-pov4` (which also rebuilds its word table), then from `tools/language/grammar/` run `node extract.mjs && node blocks.mjs && node render.mjs` — that refreshes pov4.json, blocks.json, `source/parser/pov4schema.h` (the block schema the `.pov4` static checker rejects unknown items by) and `doc/language-4-grammar.md`. `node tools/language/vscode.mjs` refreshes the extension's syntaxes and block tables. Check with `node --test test/` in `tools/language/grammar/` and the suites under `extensions/vscode/test/`.
- An item inside a block needs its `blocks.json` entry — mined from the classic parser's expect-loops and from the text-matched contextual comparisons (`CurrentTokenText() == "word"`), so a new contextual keyword flows into the schema on regeneration without being listed by hand — or the `.pov4` static checker rejects scenes that the classic parser accepts, and the two languages drift apart in silence. The `--inspect` flag prints what was mined from which function.
- Document the feature in the same PR: its manual section under `doc/html/` with the chapter's table-of-contents entry, a line in `changes.txt` (note which words are matched by text and stay free), and `doc/scene-language-4.md` when the 4.0 language surface moves.
- Add render regression scenes that exercise the new settings — the accepting path, each warning, and the failure paths — as `tests/render/<feature>.pov` with a `tests/render/<feature>.sh`, and register the script in the `make check` recipe in `Makefile.am`; an unregistered suite is a suite that never runs. A user-facing feature also gets a `distribution/scenes/` example. For 4.0 language changes keep the conversion tooling honest: `tools/language/codemod/test` and `tools/language/eval` over a scene that uses the new surface.
