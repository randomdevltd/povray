3.13 Scene Language 4.0

POV-Ray reads two scene languages. The classic language is the one every earlier version reads: .pov and .inc files, with the # directives that run while the file is read. The 4.0 language is read from .pov4 and .inc4 files. It keeps the object syntax (sphere { <0, 1, 0>, 1 texture { T } } is valid in both) and replaces everything around it: declarations, macros, loops, conditions and includes become ordinary statements of a small programming language, with no # meta-language. Classic scenes keep working unchanged and nothing is removed from the classic language.

This chapter explains why the 4.0 language exists, describes it, shows how to convert existing scenes with the codemod tool, walks through a migration, and says when a file is better left in classic.

Note: A listing that begins with a camera and a light_source is a complete scene that renders as it stands. The other listings are parts of scenes, or whole scenes that leave the camera and light to the reader. Every 4.0 listing in this chapter parses with the 4.0 grammar. To keep them short, the complete scenes leave out global_settings { assumed_gamma 1.0 }, which POV-Ray asks every scene since version 3.7 to state, and warns about when it is missing; write it in your own scenes.

3.13.1 Why a New Language

This section states plainly what is wrong with the classic grammar, with small examples. Each one is valid classic and renders as it should; the trouble is what it costs to read, check and convert such text. None of it changes: classic scenes keep their #version defaults and keep rendering the way they always have.

3.13.1.1 Two Languages in One File

A classic scene file holds two languages at once. One is the object language, sphere { ... }, texture { ... }, translate x. The other is the # meta-language: #declare, #macro, #if, #while, #include. The meta-language has its own statements, scoping rules and expression evaluator, it runs while the file is read, and a directive may stand between any two tokens of the object language. A classic file is therefore not a tree of blocks. It is a stream of text that the directives edit before the object parser sees it, and nothing can say what it means without running it.

#macro Row(N)
  #local I = 0;
  #while (I < N)
    sphere { <I, 0, 0>, 0.4 }
    #local I = I + 1;
  #end
#end

This macro counts with a variable that it changes by hand, inside a loop made of directives, around objects that the loop repeats. In 4.0 the same text is a function with a for statement: fn Row(N) { for (I = 0 to N - 1) { sphere { <I, 0, 0>, 0.4 } } }.

3.13.1.2 Directives That Splice Partial Constructs

Because a directive edits the token stream, it may open a block in one branch and close it outside the conditional, or choose one half of a construct:

#if (Fuse)
  union {
#else
  merge {
#end
    sphere { 0, 1 }
    sphere { x, 1 }
  }

This is valid classic. The text inside the directive, union {, is not a complete block, so no grammar that reads the file as written can place it: the Tree-sitter grammar for classic reports a syntax error there, and the codemod refuses the file. This listing and the macro in the next section are the only classic listings in this chapter that the classic grammar rejects.

A conditional can also stand in the middle of an expression:

sphere { 0, 1 pigment { color rgb <1, #if (Hot) 0.2 #else 0.8 #end, 0> } }

When both branches are one complete value, as here, nothing is lost, and in 4.0 this is the conditional operator: color rgb <1, Hot ? 0.2 : 0.8, 0>. When a branch is several tokens, the result depends on how its text regroups with the operators around the directive:

#declare V = 3 * #if (A) 1 + 2 #else 4 #end;

The codemod refuses this one too (splice-precedence), because the 4.0 conditional cannot be written without choosing a grouping the author may not have meant.

3.13.1.3 Building Tokens with Macros

A classic macro is a piece of text that is read again at every call. Its body does not have to be a complete construct, and it is not read as one until it is called:

#macro Begin() union { #end

Begin()
  sphere { 0, 1 }
}

The braces balance only across the macro boundary. A macro like this one cannot be checked where it is written, it is not checked at all unless it is called, and an error inside it is reported at every call. Loops work the same way: #while and macro calls move back to an earlier place in the file and read it again, which is why they could be slow (classic parsing now lexes each file once and replays the stored tokens, see Classic Parsing Speed). The meaning is unchanged: a macro is text to read again, never a function with a body that is known when it is declared.

3.13.1.4 Meaning That Depends on Runtime Values

In classic, what a name refers to, and whether a statement changes a variable, can depend on how the macro was reached:

#macro Show()
  sphere { 0, Radius }
#end
#macro Caller()
  #local Radius = 2;
  Show()
#end
Caller()

Radius is not a parameter or a global of Show. It is found because classic resolves names through the stack of calling macros, so Show reads a local of Caller, and fails with a different caller. 4.0 uses lexical scope: a function sees its own parameters and bindings, the bindings it was written inside, and the file's, never those of whoever calls it.

#macro Twice(V) #declare V = V * 2; #end
#declare X = 3;
Twice(X)

Here the macro changes the caller's X, because classic passes a variable by reference when the macro assigns its parameter. 4.0 passes every argument by value; the 4.0 form is X = Twice(X);. A #declare inside a macro is global or local depending on what ran before it, and whether A [1] indexes an array or starts a new item depends on what A currently holds. The codemod refuses the cases it cannot decide from the text (by-reference-argument, dynamic-scope, declare-maybe-local, ambiguous-index).

3.13.1.5 Optional Commas and Signs

Commas between vector components and macro arguments are optional in classic, and - is both a binary and a unary operator. Together they make a list of numbers easy to misread:

#declare A = <1 2 3>;      // <1, 2, 3>
#declare B = <1 -2 3>;     // <-1, 3>: the 1 -2 is a subtraction
#declare C = <1, 2 -3>;    // <1, -1>

The same ambiguity is why translate -x works (translate is a keyword, so the -x that follows is a negated vector) while 1 -x is a subtraction. 4.0 keeps the rule that an item starting with -, +, < or ( continues the expression before it, but its vectors and argument lists need their commas, so <1, -2, 3> is always three components, and <1 -2 3> is a syntax error instead of a two-component vector. The codemod inserts the commas.

3.13.1.6 Operators

In classic & and | share one precedence level and group from the left, and so do = and the other comparisons. = is also the assignment sign of #declare, and an equality test in a condition:

#declare T = (1 | 0 & 0);     // 0: the same as ((1 | 0) & 0)

In 4.0, && binds tighter than || as in C, so (1 || 0 && 0) is 1, and equality is ==. The codemod rewrites the operators and adds parentheses where a classic expression would otherwise change its meaning.

3.13.1.7 What Stays the Same

Everything that makes a scene look the way it does is unchanged: the object, texture, camera and light blocks, the built-in functions, and the render-time function language inside function { }. A classic file keeps its extension and its #version, and a classic file does not need to know that 4.0 exists. A 4.0 file can include classic files and call classic macros, including the standard include library, so a scene can move one file at a time. The codemod converts the files it can and leaves the others as they are.

3.13.2 The 4.0 Language

This section is the reference for the 4.0 language. It describes what the evaluator does, and uses the object syntax of the rest of this manual unchanged. The grammar is in libraries/tree-sitter-pov4 and the full design notes are in doc/scene-language-4.md in the source.

3.13.2.1 Files and the Extension

.pov4A 4.0 scene, the file that is rendered.
.inc4A 4.0 include file. It runs in the scope of the file that includes it, as a classic include does.
anything elseClassic: .pov, .inc, .mcr and any other name.

The extension is the opt-in. POV-Ray picks the front end by the name of the input file before it reads a byte, so there is no marker to write inside the file and none is accepted. This keeps the two languages from being confused: a classic file never changes meaning because someone added a word to it, a 4.0 file is never read by the classic parser, and editors and tools choose a grammar by the extension without reading the content. A 4.0 file always runs with language version 4.0, which means the same defaults as a classic scene that begins with #version 4.0; (see Switch to the 4.0 Defaults). A 4.0 file has no #version directive.

camera { location <0, 2, -6> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
sphere { <0, 0.5, 0>, 0.5 pigment { rgb <0.8, 0.2, 0.1> } }
plane { y, 0 pigment { checker rgb 1, rgb 0.4 } }

A classic file cannot include a 4.0 file. A 4.0 file can include classic files, see Mixing with Classic.

3.13.2.2 The Execution Model

A 4.0 file is a program that runs once to build the scene. As it runs, it emits items into an output. What the output is depends on where the code runs:

the top level of a .pov4 file, or of an .inc4 it includesthe scene
a function bodythe result of the function, a fragment
a block body, such as union { }the contents of that block
an array literal [ ]the elements of the array

An item is anything that can appear in a classic block body: a keyword (translate, hollow), a value (<1, 0, 0>, 2.5, "name"), a block (pigment { }) or a bracket group ([0.5 color Red]). Statements (let, if, for, while, return, include) emit nothing themselves; their bodies emit into the enclosing output.

A statement manifests its result when its output is the scene. A let never manifests:

camera { location <0, 2, -6> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
let Ball = sphere { 0, 1 pigment { rgb <1, 0, 0> } };
Ball
object { Ball translate x * 3 }

The first line that mentions Ball binds the sphere and puts nothing in the scene. The bare Ball then manifests one sphere, and the object block a second.

At the top level only things that can stand in a scene are allowed: objects, camera, light_source, background, fog, sky_sphere, rainbow, media, global_settings, default, photons and radiosity. A bare number, vector or modifier there is an error that names the line: A float cannot appear at the top level of a scene.

3.13.2.3 Functions as Components and Fragments

A function body emits into the function's result. Nothing reaches the scene unless the caller puts it there, and where a call stands decides what happens:

camera { location <0, 3, -9> look_at <0, 1.5, 0> }
light_source { <5, 8, -6> rgb 1 }
fn Tree(H) {
  cylinder { 0, y * H, 0.1 pigment { rgb <0.4, 0.3, 0.2> } }
  sphere { y * H, H / 3 pigment { rgb <0.1, 0.5, 0.1> } }
}

Tree(2)                                   // a statement at the top level: both objects manifest
let T = Tree(3);                          // an assignment: nothing manifests, T holds a fragment
union { ...T translate x * 4 }            // spread the items of T into a union
union { Tree(1) translate -x * 4 }        // a call in a block body splices its items there

A fragment is the ordered list of items that a call emitted. It behaves as:

  • its single item when it has exactly one and is used as a value (let V = Perp(A); where Perp emits one vector);
  • its items spliced in place when it is used in a block body, in an array literal, or with ...;
  • an error anywhere else, such as arithmetic on a fragment of two items.

return E; ends the function with the result E. Returning a value after the function has already emitted items is an error. A function that emits nothing and does not return gives null.

camera { location <0, 2, -6> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
fn Clamp(V, Lo = 0, Hi = 1) {
  if (V < Lo) { return Lo; }
  if (V > Hi) { return Hi; }
  return V;
}
sphere { 0, 1 pigment { rgb Clamp(1.5) } }

fn Name(A, B = 1) { ... } is a shorthand for binding a lambda, let Name = (A, B = 1) => { ... };, in the current scope. Parameters may have defaults. Functions are closures. Arguments are passed by value: arrays and dictionaries are copied when written to, so a function never changes its caller's array.

3.13.2.4 Bindings: let, Assignment and global

  • let X = E; binds X in the current function scope. The file is the outermost function. Running let X again in the same scope rebinds it. The bodies of if, for and while do not open scopes.
  • X = E; assigns to the nearest existing binding of X: a local, an enclosing function's, or the file's. It is an error if there is none. A[I] = E; and D.K = E; assign into an array or dictionary, and V.x = E; sets one component of a vector or color (a color channel is rounded to color precision).
  • global X = E; binds X at file scope from anywhere. It is what #declare does inside a classic macro.
  • let X; declares X as null. defined(X) is false while X is null, so X = null; does the job of #undef X.
camera { location <0, 3, -9> look_at <0, 1, 0> }
light_source { <5, 8, -6> rgb 1 }
let Count = 0;
fn Ball(X) {
  global Count = Count + 1;
  sphere { <X, 0.5 * Count, 0>, 0.4 pigment { rgb <1, 0.5, 0.2> } }
}
Ball(-2) Ball(0) Ball(2)
let Spare;
if (!defined(Spare)) { box { <-3, -1, -1>, <-2.5, 0, 1> pigment { rgb 0.7 } } }

An .inc4 include runs in the including file's scope, so its let bindings are visible afterwards.

3.13.2.5 Control Flow

The statements are if, while, two forms of for, break and continue. Bodies always take braces. There is no switch; the codemod writes an if chain.

if (X > 1) { ... } else if (X < 0) { ... } else { ... }
while (X < 10) { ... }
for (I = 0 to 10) { ... }            // inclusive, step 1
for (I = 0 to 1 step 0.1) { ... }
for (V in Points) { ... }            // an array, the keys of a dictionary, or a fragment
break;   continue;

for (I = A to B step S) follows the classic #for exactly, including the value of the counter afterwards: after for (I = 0 to 10) the variable I is 11.

camera { location <0, 3, -9> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
let Sizes = { small: 0.2, big: 0.45 };
let I = 0;
while (I < 5) {
  let R = (I < 2) ? Sizes.small : Sizes.big;
  if (I == 3) { I = I + 1; continue; }
  sphere { <I - 2, R, 0>, R pigment { rgb <I / 4, 0.5, 1 - I / 4> } }
  I = I + 1;
}
for (A = 0 to 1 step 0.25) { box { <A * 4 - 2, -1, 1>, <A * 4 - 1.8, A - 1, 1.2> pigment { rgb 1 } } }
let Total = 0;
for (K in Sizes) { Total = Total + Sizes[K]; }
sphere { <0, 2, 0>, Total / 2 pigment { rgb <1, 1, 0.2> } }

This scene skips the fourth sphere with continue, and its last loop adds up the two entries of a dictionary: a for (K in D) loop visits the keys.

3.13.2.6 Expressions and Precedence

postfixcall f(a, b), index a[i], member v.x d.key
prefix- + !
multiplicative* /
additive+ -
relational< <= > >=
equality== !=
logical and&&
logical or||
conditionalC ? A : B
lambda(params) => expr, (params) => { body }, P => expr

The table runs from the tightest binding to the loosest. These are the changes from classic expressions:

  • Equality is ==. It keeps the classic epsilon comparison, so (0.1 + 0.2 == 0.3) is 1. The single = is assignment only.
  • The logical operators are && and || (classic & and |), && binds tighter than ||, and both short-circuit when the left operand is a float that decides the result.
  • Comparisons and logical operators need parentheses except in conditions. As in classic, < would otherwise open a vector. They are free in if (...), while (...) and render-time function bodies. Block items, vector components, let values and arguments take only + - * /, so write (I < 2) ? A : B and filter(L, (P) => (P > 0)). This is also why box { <0, 0, 0> <1, 1, 1> } is two vectors and why a > always closes a vector.

Everything else is classic: float to vector promotion, the members .x .y .z .t .red .green .blue .filter .transmit, the names x y z t u v pi clock, and every classic built-in function.

camera { location <0, 2, -6> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
let Eq = (0.1 + 0.2 == 0.3);
let Big = (Eq && 2 > 1);
sphere { 0.5 * y, Big ? 0.5 : 0.25 pigment { rgb <1 - Eq, Eq, 0.2> } }

Literals:

<1, 2, 3>                          // a vector: 2 to 5 components as a value
rgb <1, 0.5, 0>                    // color expressions, as in classic
[1, 2, 3]   [...A, 4]              // an array, and a spread
[for (I = 0 to 9) { I * I }]       // a comprehension: an array that is an output
{ A: 1, "b c": 2, [K]: 3, ...D }   // a dictionary
null   true   false

Color expressions are as in classic. rgb, rgbf, rgbt, rgbft, the srgb forms and color/colour are prefix operators that take the whole expression after them, so rgb <1, 0, 0> * 0.5 is half red. The channel words red, green, blue, filter, transmit and alpha each take a value, so let C = color red 1 green 0.5 filter 0.1; works in a let as it does in a block body. A color is a five-component vector rounded to the renderer's color precision, exactly as a classic color identifier.

3.13.2.7 Arrays, Comprehensions and Dictionaries

An array literal is an output, so if, for and let work inside it and a for in an array literal is a comprehension. Items are separated by commas or just by juxtaposition. An array has a fixed size once it is built: A[I] = E replaces an element, and push(A, V) returns a longer copy.

A dictionary maps names to values. Any word, string or computed [string] may be a key, reserved or not ({ step: 1 }), and member access takes any word (D.step). On vectors and colors the members are the classic component names.

camera { location <0, 3, -9> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
let N = 8;
let Ring = [for (I = 0 to N - 1) { <3 * cos(I * tau / N), 0.3, 3 * sin(I * tau / N)> }];
let Style = { r: 0.3, "paint color": rgb <0.9, 0.7, 0.1>, [concat("sh", "ine")]: 0.8 };
let Plain = { ...Style, r: 0.4 };
for (P in Ring) { sphere { P, Plain.r pigment { Plain["paint color"] } finish { phong Style.shine } } }
let Grid = array(2, array(3, 0.5));
Grid[1][2] = 1;
sphere { <0, len(Grid) + Grid[1][2], 0>, 0.5 pigment { rgb 1 } }

This builds a ring of spheres from a comprehension, copies and overrides a dictionary, and builds a two-dimensional array. An array whose elements are all arrays of the same shape counts as a classic multi-dimensional array for dimensions, dimension_size and for classic code: array(4, array(10)) has two dimensions and reaches a classic include as array[4][10].

In a block body a bracket group is emitted as written, so classic map entries keep working: color_map { [0 color Red] [1 color Blue] }. Indexing and member access take no space before the [ or .: A[I] indexes, and A [I] starts a new item.

3.13.2.8 Lambdas and the Conditional Operator

A lambda is a function without a name. Its body is an expression, or braces for a body that emits items; map and filter take them.

camera { location <0, 3, -9> look_at <0, 1, 0> }
light_source { <5, 8, -6> rgb 1 }
let Scale = (S) => S * 2;
let Points = map(range(0, 9), (I) => <I - 4.5, Scale(sin(I)), 0>);
let Up = filter(Points, (P) => (P.y > 0));
for (P in Up) { sphere { P, 0.3 pigment { rgb <P.y / 2, 0.4, 0.8> } } }

range(A, B) includes both ends and steps as the classic #for, and the lambda in filter returns a condition, so its comparison has parentheses. A { after => always starts a body. Write => ({ ... }) for a lambda that returns a dictionary.

The conditional operator C ? A : B replaces the #if that stood inside an expression:

// classic:  color rgb <1, #if (Hot) 0.2 #else 0.8 #end, 0>
color rgb <1, Hot ? 0.2 : 0.8, 0>

3.13.2.9 Blocks

keyword { body } is a block. Its body is an output, so it may hold statements. A statement's emitted items land where it stands, which is why a block can mix classic items and logic:

camera { location <0, 3, -9> look_at <0, 1, 0> }
light_source { <5, 8, -6> rgb 1 }
let Shiny = true;
let Big = true;
let Spheres = [for (I = 0 to 3) { sphere { x * I, 0.4 } }];
union {
  ...Spheres
  pigment { rgb <0.2, 0.6, 0.9> }
  if (Shiny) { finish { phong 1 } }
  translate <-2, 1, 0>
  scale if (Big) { 1.5 } else { 1 }
}

The grammar does not know which items each block accepts: sphere { } and pigment { } are both a keyword and a body. The renderer's object builders check the contents, as they do for classic scenes.

A value used as an item in a block body is emitted according to its kind. A number, vector, color or string is emitted as itself. An object becomes object { V }. A texture inside texture { } is V, and so on. A value that follows the keyword of its own kind is emitted bare (transform T), and so is an object written first in an object block that is not a CSG block or a light_group, which classic reads as a copy to modify: light_source { Lamp translate y }. Values spliced from a spread or a call are separated by commas, so sphere_sweep { linear_spline 4, ...Points } reads as written. An array must be spread (...A), never placed in a body whole.

A binding may be a run of blocks. let T = texture { ... } texture { ... }; binds a fragment of both, a layered texture, and T or ...T in an object body emits both, as texture { T } does in classic.

camera { location <0, 3, -9> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
let Lamp = light_source { <4, 6, -3> rgb 0.4 };
light_source { Lamp translate y }
let Glaze = texture { pigment { rgb <0.9, 0.5, 0.2> } } texture { pigment { rgbt <1, 1, 1, 0.7> } finish { phong 1 } };
sphere { 0, 1 ...Glaze }

3.13.2.10 Render-time Functions

function { ... } and function(x, y, z) { ... } blocks keep the classic render-time function language, which compiles to the function VM. Inside them a name bound by let to a number is replaced by its value, and a name bound to a render-time function is called, as in classic. The body uses the 4.0 operators, and the renderer lowers it to the classic function language: == to =, && to &, C ? A : B to select(-abs(C), A, B) and !C to select(-abs(C), 0, 1). The image-size form function 300, 300 { pigment { ... } } is kept.

camera { location <0, 2, -5> look_at <0, 0, 0> }
light_source { <-4, 6, -6> rgb 1 }
let K = 3;
let Amp = 0.3;
isosurface {
  function { sqrt(x * x + y * y + z * z) - 1 + Amp * sin(K * x) * sin(K * z) }
  contained_by { box { -1.5, 1.5 } }
  max_gradient 4
  pigment { rgb <0.5, 0.8, 0.5> }
}

A 4.0 lambda exists only while the scene is built and cannot be called from a render-time function. Built-in constants (x, pi, clock) are not callable, so translate x (2) is an error. trace(O, P, D, N) sets the 4.0 variable N to the surface normal, binding it if needed.

The portal target block portal { ... to { ... } } is a block named to, which stays a keyword of for (I = A to B) elsewhere (see Portals and Screens).

3.13.2.11 Built-ins Added by 4.0

len(A)The number of elements of an array.
range(A, B[, S])The array of numbers from A to B, inclusive, with the classic #for stepping.
map(A, F)The array of F applied to each element.
filter(A, F)The elements for which F is true.
push(A, V)A new array with V added at the end.
keys(D)The keys of a dictionary, as strings.
defined(Name)False when the name is unbound or null.
debug(S), warning(S), error(S)The classic #debug, #warning and #error.
array(N[, Fill])An array of N elements, all null or all Fill.

The words let, fn, return, null, in, step and continue are reserved in 4.0 beside the classic reserved words, and a name cannot be a reserved word. len, map, push and keys are not reserved: a name resolves to a 4.0 binding first, then to a classic declaration of that name, then to the built-in. Names that start with __pov4_ belong to the evaluator.

Comments are // and /* */ (not nested). A ; after an item is allowed and ignored; let, assignment, global, include and return statements end with ;.

3.13.2.12 Mixing with Classic

A .pov4 file may include a classic file. The classic parser reads it into the same scene, its declarations become visible to the 4.0 program by name, and its macros can be called from 4.0 code. The call is handed to the classic parser where it stands: in place inside a block body, as a scene item at the top level, and through #declare where a value is needed. A classic include in a block body is handed over in place too (union { include "parts.inc"; }). This is how a 4.0 scene uses the standard include library unchanged: include "colors.inc"; and include "textures.inc"; work as they are.

The two sides see each other's names like this:

  • Classic sees 4.0 bindings. Before a classic include or a classic macro call is read, the evaluator declares every file-scope binding that changed since, as a classic identifier. Floats, vectors, colors, strings, non-empty arrays, dictionaries, layered textures, and objects and other handles (by copy) are declared. Functions, null, undeclarable blocks and other fragments are not.
  • Classic owns a value once it has it. From the point where a binding is handed over until the block reaches the classic parser, a second call in the same block sees what the first call left, unless 4.0 assigns the binding again in between.
  • 4.0 reads back what classic changed. After a classic include, a top-level macro call, a macro call used as a value, or a block containing macro calls, the floats, vectors and strings that the classic code changed are read back into their 4.0 bindings. Other classic changes are seen through names that no 4.0 binding hides.

A classic include file and the 4.0 scene that uses it:

// shelf.inc
#declare Shelves = 0;
#macro Shelf()
  box { <0, 0, 0>, <ShelfWidth, 0.08, 0.5> pigment { rgb <0.6, 0.4, 0.2> } }
  #declare Shelves = Shelves + 1;
#end

camera { location <0, 2, -9> look_at <1, 1.2, 0> }
light_source { <5, 8, -6> rgb 1 }
include "shelf.inc";
let ShelfWidth = 3;
for (K = 0 to 2) { object { Shelf() translate y * K * 0.8 } }
sphere { <1.5, 0.33 + (Shelves - 1) * 0.8, 0.25>, 0.25 pigment { rgb <0.9, 0.2, 0.2> } }

Shelf reads ShelfWidth, which only the 4.0 file binds, and the 4.0 file reads the Shelves counter that the macro keeps in classic. A classic file cannot include a 4.0 file, and a classic include cannot call back a 4.0 function: pass data to the classic file instead.

3.13.2.13 Errors and Where They Are Reported

An error in 4.0 code is reported as file:line:column: message. There are two kinds, and both are located in the .pov4 file:

  • The evaluator finds it when the program itself is wrong: an unknown name, a missing binding, a fragment used as a value, a bare value at the top level.
  • The object builder finds it when the program ran correctly but the scene text it produced is wrong, such as a keyword that its block does not accept.
camera { location <0, 2, -7> look_at <0, 1, 0> }
let R = 1;
sphere { 0, Radius }

File 'e1.pov4' line 3: Parse Error: e1.pov4:3:13: Unknown name 'Radius'.

The name is not bound, so the evaluator stops at line 3, column 13. The next scene runs without trouble, but height_field is not a keyword of a sphere:

camera { location <0, 2, -7> look_at <0, 1, 0> }
let R = 1;
sphere {
  0, R
  height_field 2
}

File 'e2.pov4' line 3: Possible Parse Error: Unmatched {
File 'e2.pov4' line 5: Parse Error: No matching }, height_field found instead

This message comes from the classic object builder, with the line of the .pov4 item it came from. To make that possible, the evaluator hands the scene text it builds to the classic parser in batches of up to 1 MiB per file, with a table that maps every line back to the source, so a loop that makes thousands of objects does not lose its place. An error in an included .inc4 file names that file and its line.

A long loop reports parse progress and can be cancelled like a classic parse. The built-in error(S) raises an error of your own with the location of the call.

3.13.2.14 Limits and Testing Options

The evaluator runs on its own stack of 256 MiB (Linux and Windows; elsewhere it uses the stack of the parser thread). These limits apply:

  • Function calls nest at most 10,000 deep. Classic allows about 100 nested macro calls.
  • Statements, expressions, blocks and nested arrays and dictionaries nest at most 100,000 levels in total, counting every active call and the parse of an .inc4 included at that point.
  • .inc4 includes nest at most 100 deep. Each file is parsed once and reused.
  • An array holds at most 256 MiB of values, which is 4,194,304 elements on a 64-bit build. This bounds literals, comprehensions, range, array and push.
  • int, div, chr, bitwise_* and random streams reject values outside the integer range. div by zero is an error. A NaN is an error.

Two options exist for testing and are not part of the language:

Pov4_Version=n.n
+MLn.n		Run a 4.0 scene under an older language version. It is how a converted scene is compared with its classic original.
Pov4_Lowered_File=file
+GLfile		Write the classic scene text that the 4.0 scene was lowered to. Rendering that file gives the same image.

The lowered file is the classic text that the classic parser actually reads, with every expression already evaluated. It is useful to see what a 4.0 construct becomes, and to isolate a problem to one of the two front ends:

povray +Iscene.pov4 +GLscene_lowered.pov
povray +Iscene.pov4 +ML3.7

The first command renders scene.pov4 and also writes scene_lowered.pov. The second renders it with the defaults of language version 3.7 instead of 4.0. For the scene of The Execution Model, with its camera and light, the lowered file is:

#version 4;
camera { location <0, 2, -6> look_at <0, 0.5, 0> }
light_source { <5, 8, -6> rgb 1 }
#declare __pov4_1 = sphere { 0, 1 pigment { rgb <1, 0, 0> } };
object { __pov4_1 }
object { __pov4_1 translate <3, 0, 0> }

The scene starts with #version 4;. Every let that binds a block becomes a #declare of a name that begins with __pov4_, and each manifested item becomes the classic text for it.

3.13.3 Converting Scenes with the Codemod

The codemod, tools/language/codemod/codemod.mjs in the source tree, converts well-formed classic files to 4.0. It works on the classic syntax tree and makes text edits: directives and operators are rewritten, and everything else (comments, layout, the bodies of objects) is kept byte for byte, so the result still looks like the file you wrote. A scene it cannot convert safely is refused with a line, a column and a reason, and nothing is written for it. The codemod is a Node.js program that uses the Tree-sitter grammar in libraries/tree-sitter-pov, which needs its dependencies installed once (libraries/tree-sitter-pov/README.md has the steps).

3.13.3.1 Running It

node tools/language/codemod/codemod.mjs SCENE.pov... -o OUT_DIR [--includes classic|convert] [-L DIR]... [--json REPORT] [--quiet]
SCENE.pov or a folderOne or more scenes. A folder is searched for .pov files. A .pov input becomes a .pov4 file with the same relative path in the output folder.
-o OUT_DIRRequired. The folder that receives the converted files.
--includes classicThe default. The converted scene includes its classic files as they are (include "colors.inc";).
--includes convertAlso convert every include the scene reaches, and write each as an .inc4 beside the scene. Includes that are refused, or not found, stay classic.
-L DIRA library folder to search for includes, as with POV-Ray's +L. The search order is the scene's folder, then the -L folders, then distribution/include. May be repeated.
--json REPORTWrite a report of every scene and file: its output, refusals and notes.
--quietPrint refusals only.

It prints one line per file, converted with the input and output, or refused with file:line:column, the reason and a detail, and then how many scenes were converted. The exit status is 0 when every scene converted and 2 when at least one was refused. An include named with .. or an absolute path is written by its file name, so nothing lands outside the output folder.

$ node tools/language/codemod/codemod.mjs garden.pov -o out
converted	garden.pov	out/garden.pov4
1/1 scenes converted

Scope. The codemod follows the way classic resolves a declaration. At file level both #declare and #local bind in the file, as let X, unless an earlier unconditional binding of X in the same or an enclosing statement list makes it X =. In a macro, #local X is let X (or X = after a binding, or for a parameter), and #declare X is X = for a parameter or a local that dominates it and global X = otherwise.

Notes. Two conversions are correct but change something worth knowing, so the codemod records a note in the report. An include's top-level #local becomes let (include-local): classic drops it at the end of the include, and an .inc4 leaves it in the scope of the file that includes it. A file-level binding whose name a classic include reads (read-by-classic-include) is noted because the classic include must see the 4.0 binding as it saw the classic one, which it does.

3.13.3.3 What It Refuses

A file is well-formed when every directive stands at a statement or block-item boundary, or inside an expression where it is a complete conditional. Anything else is refused: the report names the file, line, column and reason, and that file is not converted. If a scene includes a refused file with --includes convert, the include stays classic and the scene is still converted.

syntax-error, partial-macro, stray-itemThe file does not parse, or a macro builds tokens for its caller, or a keyword or call stands at statement level outside a macro. By hand: complete the construct, for example write both branches of a split #if as whole blocks. A macro that opens or closes a block for its caller stays classic.
file-io#fopen, #fclose, #read, #write. 4.0 has no file I/O. Keep that code in a classic include and call it from the 4.0 scene.
ambiguous-indexAn identifier followed by a spaced [, which classic decides by the type of the identifier. Add a comma, or write the index without a space.
expression-if-without-else, expression-if-not-single-value, directive-in-expression, operator-spliceA conditional in a value position that has no #else, or a branch that is not exactly one value, or another directive in a value position, or a splice after a unary sign. By hand: give the conditional an #else, or write it as a statement.
by-reference-argumentA macro assigns a parameter that the caller passed as a variable that is read again. Classic writes the value back, 4.0 passes by value. By hand: return the value, X = Twice(X);.
dynamic-scopeA macro reads or declares a name that is local to a macro that calls it. By hand: pass the value as a parameter.
declare-maybe-local#declare X in a macro that makes X local on some paths only. By hand: decide whether X is a let or a global.
layered-texture#declare T = texture { } texture { } has no single value in the codemod's output. By hand: let T = texture { } texture { };, which binds a fragment of both.
tuple, optional-parameter, optional-declare, scope-prefixTuples, optional, and local. or global. prefixes. By hand: a default parameter (B = null with defined(B)), or global.
include-local-shadowWith --includes convert, an include's top-level #local X where the scene or another include binds X too. By hand: rename one of them.
called-by-classic-includeA macro of the scene that a classic include calls back. A classic file cannot call a 4.0 function. By hand: keep that macro in a classic file, or pass the data instead.
splice-precedenceAn #if in an expression whose branch would regroup with the operator around it, as in 3 * #if (A) 1 + 2 .... By hand: parenthesize the branch in the classic file first.
array-sizeAn array initializer with directives in it and a size, whose element count is not known. By hand: write the array as a literal or a comprehension.
switch-fallthrough, break-placementA #case that runs on into the next one, or a #break that is not the last item of a clause or is outside a loop. By hand: repeat the shared items or restructure.
empty-argumentA macro call such as M(1,,3) that leaves an argument out. By hand: pass a value.
directive-in-dictionary, nested-commentA directive in a dictionary literal, or a nested /* */ comment. 4.0 has no form for either.

For example, all of these are refused with the reason shown:

refused	by-reference.pov:3:7	by-reference-argument	Twice assigns its parameter V, passed X
refused	dynamic-scope.pov:2:15	dynamic-scope	Radius in Show reads a local of calling macro Caller
refused	maybe-local.pov:3:3	declare-maybe-local	Size is #local in Pick on some paths only
refused	layered.pov:1:14	layered-texture	a declared layered texture has no 4.0 value form
refused	splice-prec.pov:2:26	splice-precedence	1 + 2 would regroup with the operator around the #if
refused	calledback.pov:2:1	called-by-classic-include	a classic include calls Hook, which would become a 4.0 function
refused	file-io.pov:1:1	file-io
refused	splice.pov:3:9	syntax-error

3.13.3.4 Checking a Conversion

A conversion is right when the converted scene, run with the language version of the classic one, makes the same picture as the classic scene. Language version is the whole difference between the two: a 4.0 scene always runs with the 4.0 defaults, so to compare like with like, tell POV-Ray to run it at the old version with +ML:

povray +Iscene.pov +W160 +H120 -A +FP16 +Oclassic.ppm
povray +Iout/scene.pov4 +ML3.7 +W160 +H120 -A +FP16 +Oconverted.ppm

If the scene's first #version was 3.7, write +ML3.7, and so on for the version it declared; a scene with no #version passes nothing. The two images must be pixel for pixel the same. A difference is either a defect of the conversion or of the evaluator, which is worth a bug report with the smallest scene that shows it, or a classic scene that was plainly wrong and that the converted one gets right, which is worth a look before assuming either.

For many scenes there is an evaluation tool, tools/language/eval/eval.mjs. It converts every scene under a folder and renders three images of each at 160x120 without anti-aliasing:

AThe classic scene as it is.
BThe converted scene, run with the classic scene's language version.
CThe converted scene, run as 4.0.

A different from B is a conversion or evaluator defect. B different from C is the effect of the 4.0 defaults on that scene, which the tool reports for review, since a different picture is often the better one. eval all --out DIR --povray BIN runs the three steps, and plan, render and report run alone. Each scene is identical, noise-level, different, conversion-refused, eval-error, render-error or timeout, and the report page shows the flagged scenes with A, B, C and difference maps. doc/scene-language-4.md describes the tool in full.

3.13.4 Migration Guide

These steps take a classic scene to idiomatic 4.0 and check each one. They can stop at any point: a converted scene that runs at its old version is already a valid 4.0 scene, and the later steps are choices.

The examples use a small fence scene with macros, a counter loop and a conditional:

#version 3.7;
global_settings { assumed_gamma 1.0 ambient_light rgb 8 }

camera { location <0, 1.6, -6> look_at <0, 0.8, 0> }
light_source { <6, 10, -8> rgb 1 }
sphere { 0, 100 pigment { rgb <0.4, 0.6, 1> } finish { diffuse 0 } }
plane { y, 0 pigment { rgb <0.3, 0.5, 0.2> } }

#declare Wood = texture { pigment { rgb <0.55, 0.35, 0.2> } }

#macro Post(H, Round)
  #if (Round)
    cylinder { 0, y * H, 0.12 texture { Wood } }
  #else
    box { <-0.12, 0, -0.12>, <0.12, H, 0.12> texture { Wood } }
  #end
#end

#macro Fence(N, Gap, Lean)
  #local I = 0;
  #while (I < N)
    object { Post(1 + 0.25 * mod(I, 2), (I = 3)) translate x * I * Gap }
    #local I = I + 1;
  #end
  box {
    <0, 0.55, -0.04>, <(N - 1) * Gap, 0.65, 0.04>
    texture { Wood }
    #if (Lean) rotate z * 2 #end
  }
#end

union { Fence(6, 0.8, true) translate x * -2 }

3.13.4.1 Step 1: Convert

Run the codemod on the scene, and on the includes it uses if you want those converted too:

node tools/language/codemod/codemod.mjs garden.pov -o out

For this scene it writes out/garden.pov4. Everything outside the directives is as it was:

global_settings { assumed_gamma 1.0 ambient_light rgb 8 }

camera { location <0, 1.6, -6> look_at <0, 0.8, 0> }
light_source { <6, 10, -8> rgb 1 }
sphere { 0, 100 pigment { rgb <0.4, 0.6, 1> } finish { diffuse 0 } }
plane { y, 0 pigment { rgb <0.3, 0.5, 0.2> } }

let Wood = texture { pigment { rgb <0.55, 0.35, 0.2> } };

fn Post(H, Round) {
  if (Round) {
    cylinder { 0, y * H, 0.12 texture { Wood } }
  } else {
    box { <-0.12, 0, -0.12>, <0.12, H, 0.12> texture { Wood } }
  }
}

fn Fence(N, Gap, Lean) {
  let I = 0;
  while (I < N) {
    object { Post(1 + 0.25 * mod(I, 2), (I == 3)) translate x * I * Gap }
    I = I + 1;
  }
  box {
    <0, 0.55, -0.04>, <(N - 1) * Gap, 0.65, 0.04>
    texture { Wood }
    if (Lean) { rotate z * 2 }
  }
}

union { Fence(6, 0.8, true) translate x * -2 }

The #version line is gone, the macros are functions, #declare became let, the counter loop is a while, and = in the comparison is now ==. If it refuses a file, see What It Refuses.

3.13.4.2 Step 2: Render at the Old Version and Compare

Render the classic scene, then the converted one with +ML set to the version the original declared:

povray +Igarden.pov +W160 +H120 -A +FP16 +Oa.ppm
povray +Iout/garden.pov4 +ML3.7 +W160 +H120 -A +FP16 +Ob.ppm

The two images must match exactly. They do for this scene: a comparison of the pixel data of the two files finds no difference. Fix any difference now, while the only thing that has changed is the language. Do not go on until it matches.

3.13.4.3 Step 3: Switch to the 4.0 Defaults and Fix the Look

Now render the converted scene with no +ML, which runs it as 4.0. A 4.0 scene gets the defaults of language version 4.0, and a scene that was written for an older version can change appearance. Each of these is a deliberate difference of the language version, not of the 4.0 language, and each has a one-line fix.

The default ambient is 0From version 3.8 a finish's default ambient is 0, where it was 0.1. Most old scenes get darker. A surface that was lit only by ambient, such as a sky dome or a backdrop with diffuse 0, goes black. The default pigment is white and the default camera right is the image aspect ratio (see below) from the same version. Fix a scene as a whole with default { finish { ambient 0.1 } }, or give the sky ambient and the other surfaces what they need.
Media renders inside solid objectsFrom 4.0, interior media are rendered inside objects that are not hollow, and inside objects nested in them. Earlier versions hid them, and warned. A scene that put media in a solid object by mistake, or that relied on a non-hollow object to hide the media around it, now shows the media. Each object also replaces the media of the objects placed before it where they overlap, unless its media set another mix, and hollow is deprecated in favor of media { mix add }. See Version Directive and Empty and Solid Objects.
3.6 scenes without assumed_gammaA scene older than 3.7 with no assumed_gamma is rendered with gamma correction turned off. A 4.0 scene without it gets assumed_gamma 1.0 implied, with a warning, so the same color values come out lighter. To keep the old look add global_settings { assumed_gamma 2.2 }, which is close but not identical, since the output is encoded as sRGB. For physically based results use assumed_gamma 1.0 and adjust the colors. See Assumed_Gamma.
Camera rightA camera with no right got x * 1.33 before 3.8 and gets the aspect ratio of the image now, so the frame of a 4:3 picture changes by a quarter of a percent. Write right x * 1.33 for the same frame, or right x * image_width / image_height to follow the image.
Refraction interior orderBefore 4.0, the innermost object entered gives the ior where objects are nested, and leaving an overlap of two objects does not refract. In 4.0 a region takes the ior of the interior placed last among those holding it, so a glass object must be placed after the water or container around it. See Refraction.
New reserved wordsThe names tags, filter_tags, front_filter_tags, back_filter_tags, any and none become reserved in a scene that runs at 4.0. The codemod renames the identifiers that collide with a reserved word, such as step or in, with a trailing _.

The fence scene shows the first of these. Run as 4.0, its sky dome is black, and its ground and fence are much darker than in the classic render, since the scene's ambient_light rgb 8 multiplied the old default ambient of 0.1. One line brings the old look back:

global_settings { assumed_gamma 1.0 ambient_light rgb 8 }
default { finish { ambient 0.1 } }

Put it at the top of the converted file, and add right x * 1.33 to the camera for the same frame as before. The result matches the classic render of step 2 exactly. If a scene's look is simply different and you prefer it, keep it. The 4.0 look is the one that the new defaults describe.

3.13.4.4 Step 4: Tidy into Idiomatic 4.0

The converted scene is a literal translation, so it still reads like the classic one. Now use what 4.0 offers:

  • Functions as components. A function that emits objects is a component. A call can stand in a block, be spread, or be kept in a let and reused.
  • Comprehensions and for instead of counters. A while loop that counts with a variable is a for (I = A to B), or a comprehension when it builds a list.
  • Default parameters instead of optional parameters and #ifdef tests.
  • ?: instead of #if splices for one value, such as rotate z * (Lean ? 2 : 0).

The fence scene, tidied, with the ambient default restored once at the top and the camera frame kept:

global_settings { assumed_gamma 1.0 ambient_light rgb 8 }
default { finish { ambient 0.1 } }

camera { location <0, 1.6, -6> look_at <0, 0.8, 0> right x * 1.33 }
light_source { <6, 10, -8> rgb 1 }
sphere { 0, 100 pigment { rgb <0.4, 0.6, 1> } finish { diffuse 0 } }
plane { y, 0 pigment { rgb <0.3, 0.5, 0.2> } }

let Wood = texture { pigment { rgb <0.55, 0.35, 0.2> } };

fn Post(H, Round) {
  if (Round) { cylinder { 0, y * H, 0.12 texture { Wood } } }
  else { box { <-0.12, 0, -0.12>, <0.12, H, 0.12> texture { Wood } } }
}

fn Fence(N, Gap, Lean = false) {
  let Posts = [for (I = 0 to N - 1) { object { Post(1 + 0.25 * mod(I, 2), (I == 3)) translate x * I * Gap } }];
  ...Posts
  box {
    <0, 0.55, -0.04>, <(N - 1) * Gap, 0.65, 0.04>
    texture { Wood }
    rotate z * (Lean ? 2 : 0)
  }
}

union { Fence(6, 0.8, true) translate x * -2 }

The posts are one comprehension, Lean is a parameter with a default, and the optional rotation is a value instead of a splice. Check the result as you did in step 2, now without +ML: it must match the classic render.

3.13.5 When to Keep Classic Files

Moving a scene to 4.0 is a choice, and a scene can use both languages at once. A 4.0 file includes classic files and calls their macros, so a classic file can stay classic for as long as it is the better tool. These are the cases.

3.13.5.1 Heavy Literal Data

A mesh written out as text, such as a mesh2 of hundreds of thousands of triangles from a modeler, is data and not code, and the classic parser reads it faster and in far less memory. Inline literal meshes in a .pov4 file are currently slower to read and much larger in memory than in classic. One measurement, on a mesh2 of 62,750 vertices and 125,000 triangles (5.7 MB of text), parsed with one thread and rendered at 8 by 6 pixels:

the mesh in a classic .pov scene0.23 seconds to parse, 38 MB peak memory
the same text inline in a .pov4 scene1.9 seconds to parse, 471 MB peak memory
the same text in a classic .inc, included from a .pov4 scene0.21 seconds to parse, 38 MB peak memory
the same geometry as a .povm file, used from a .pov4 scene22 MB peak memory (the mesh is loaded after parsing)

The numbers will differ on another machine, but the proportions are the point. Keep such data in a classic include and write include "mesh.inc"; in the 4.0 scene. For geometry that is heavy and does not change, the .povm mesh file format is better still. It holds the geometry as binary arrays that a scene loads without parsing text (see doc/povm.md in the source), and works the same from a classic or a 4.0 scene:

camera { location <0, 1, -5> look_at <0, 1, 0> }
light_source { <5, 8, -6> rgb 1 }
mesh2 { povm "trunk.povm" pigment { rgb <0.4, 0.3, 0.2> } }

3.13.5.2 The Standard Library and Third-party Includes

The standard include files (colors.inc, textures.inc, shapes.inc, math.inc and the rest) and includes written by others are classic, work from a .pov4 file as they are, and gain nothing from conversion. Write include "colors.inc";. The codemod with --includes convert can convert them, but there is no need to, and the converted copies would have to be kept in step with the originals. Leave a library classic unless you are the one who maintains it.

3.13.5.3 Includes the Codemod Refuses

Some classic text has no 4.0 form, and the codemod refuses it (What It Refuses). Leave those files classic and include them:

  • Splices of partial constructs, and macros that open or close a block for their caller.
  • File I/O with #fopen, #read and #write.
  • Macros that assign a parameter by reference, or that read names local to a calling macro.
  • Macros that a classic include calls back. A classic file cannot call a function of a 4.0 file.

3.13.5.4 Behavior That Only Classic Has

A scene that depends on a classic-only behavior stays classic. A .pov file keeps its #version and its defaults, and rendering it is unchanged. If you need an older language version (for example a 3.6 scene that must come out exactly as before), a classic scene with #version 3.6; is the faithful way. The conversion to 4.0 followed by +ML is for checking a conversion, not for running scenes for good.

3.13.5.5 Classic Parsing Speed

Classic parsing has also become faster, so staying classic does not cost the parsing speed that motivated some of the changes. Each scene or include file is lexed once into a compact array of tokens, with reserved words resolved, names interned and numbers converted. #while, #for, macro calls and returns then move an index into the array instead of seeking the file and lexing it again. Before, most of the cost of a loop was system time spent re-reading the file. On the benchmark scenes in doc/PERF.md a 50,000-pass loop that calls a macro from an include parses in 0.15 seconds instead of 0.63, and a macro loop benchmark in 0.21 seconds instead of 1.15; a 59 MB text mesh parses in 2.1 seconds instead of 2.8, with a peak of 143 MB instead of 123 MB. The section "Classic parser: lex once" of that file has the full figures.
